# Stage 12 — DormHub demo data (prepared, not executed)

This directory contains a synthetic, opt-in PostgreSQL seed. Nothing here has
been run against a database. Use only an isolated demo database after approval.

## Source of truth and limits

Backend-DormHub has no checked-in SQL migration. `application.yaml` sets
`spring.jpa.hibernate.ddl-auto: update`, so the JPA entities describe the
intended mapping, **not proof of the live database schema**. The seed checks
all referenced tables and columns inside a transaction and rolls back on an
error. A DBA must still review live constraints and triggers before execution.
The seed does not create or alter any table, column, index, or enum type.

The backend uses `BCryptPasswordEncoder`. `01_seed_demo.sql` contains no
password, password hash, actual user ID, or personal data. The operator must
supply a newly generated **temporary demo-only BCrypt hash** through a pgAdmin
session setting. Never reuse a real account's hash. Give the plaintext demo
password to testers through a separate secure channel; do not put it in SQL,
this directory, screenshots, or source control.

## Planned accounts

All emails use the reserved `.invalid` domain and all names/addresses are
synthetic. Login success has **not** been tested.

The seed requires an **existing ACTIVE MANAGER** only to populate the
non-null `room_assignments.assigned_by` foreign key. It does not create or
change a manager account.

## Data graph and constraints

`users.id → students.user_id` (unique); `buildings.id → rooms.building_id`
with unique `(building_id, room_number)`; `students.id` and `rooms.id` →
`dorm_applications`; approved application → `contracts.dorm_application_id`
(unique); contract + student + room + existing manager → `room_assignments`;
student + room → `maintenance_requests`; notification →
`notification_receivers` → user. Room + first day of month → `meter_readings`
and `invoices` (both unique by room/month); invoice → `invoice_details`.
`users.username`, `users.email`, `students.student_code`, and
`students.user_id` are unique. Identity primary keys are generated by the
database; the seed resolves all foreign keys by natural keys after insertion.

There is **no Bed entity or checked-in bed migration**, so the seed cannot
create beds without inventing a schema. It also omits `payments` and
`sepay_transactions` to avoid fabricating a completed financial transfer.
Two invoices remain `UNPAID`. No real bank account details are used.

## Manual pgAdmin run — only after approval

1. Make a backup or snapshot of an **isolated demo database**. Confirm the
   Query Tool is connected to that database and the Backend version matches
   the inspected source. Review live schema/constraints first.
2. Generate a fresh BCrypt hash **outside this repository** using a trusted
   BCrypt implementation compatible with Spring's `BCryptPasswordEncoder`.
   Do not use an existing account's hash.
3. In one pgAdmin Query Tool session, set session-only inputs (replace the
   placeholders locally; do not save or share the query):

   ```sql
   SELECT set_config('dormhub.demo_password_hash', '<temporary demo-only BCrypt hash>', false);
   SELECT set_config('dormhub.demo_manager_email', '<existing ACTIVE MANAGER email>', false);
   ```

4. Open `01_seed_demo.sql` in the **same** Query Tool connection. Review it,
   then execute once. If any preflight or constraint fails, the transaction
   must be rolled back. Inspect the error and live schema before attempting a
   revised seed. Do not bypass the preflight.
5. Run `02_verify_demo.sql` to inspect synthetic rows and relationships.
   Then manually test login on Expo Go. A successful SQL run alone does not
   prove authentication, cookies, CSRF, or Mobile integration.
6. Clear session settings or disconnect the Query Tool after use:

   ```sql
   SELECT set_config('dormhub.demo_password_hash', '', false);
   SELECT set_config('dormhub.demo_manager_email', '', false);
   ```

The seed is designed to avoid duplicate inserts. Re-running does **not**
reset modified demo passwords, account statuses, read flags, or business
states. Stop and inspect if an existing `DEMO12` record differs from the
documented scenario. Do not assume a re-run repairs test data.

## Mobile coverage limits

Backend has manager-only room listing (`/api/v1/manager/rooms`) and lacks a
student/guest room catalog endpoint. Real-student Find Room / room selection
cannot be fully tested through Mobile even with seeded rooms. Student invoice
list/detail and student utility meter-reading endpoints are absent; their UI
cannot show these seeded records through the current API. Payment history has
no student list endpoint; this seed deliberately creates no payments. There
is no bed API/entity to test individual bed assignment. These gaps are API
contract gaps, not SQL seed failures.

## Decisions required before any execution

- Which isolated PostgreSQL database and Backend revision are approved?
- Has its live schema, unique constraints, foreign keys and triggers been
  compared with the Entity mapping? (`ddl-auto:update` cannot guarantee it.)
- Which existing ACTIVE MANAGER should be used as `assigned_by`?
- Is creating seven synthetic STUDENT accounts and unpaid demo invoices in
  that database approved? Are the demo dates and amounts acceptable?
- Who will generate/distribute the temporary demo password and BCrypt hash,
  and who will run the script in pgAdmin?

No approval is inferred from this document. Do not execute the seed until
these decisions are resolved.
